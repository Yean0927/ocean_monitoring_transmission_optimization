# 海洋监测视频压缩传输实验简版汇报

## 1. 实验目标

本实验面向海洋监测平台的视频数据压缩传输优化，比较不同视频压缩方案在不同链路带宽和传输分片大小条件下的端到端效率。

实验重点是比较不同视频编码/转码方案对文件体积、编码开销、解码开销和传输时延的综合影响。
实验的主端到端结论根据时延缩短率和优化后的传输总时延；FFmpeg 解码校验耗时计入压缩方案的端到端传输总时延，同时保留解码实时倍率用于分析接收端播放适用性。

```text
T_video = T_encode + T_transfer + T_decode
latency_reduction = (T_direct - T_video) / T_direct * 100%
decode_realtime_factor = video_duration / T_decode_check
```

其中：

```text
T_direct = 原始视频文件不重新压缩时的直接传输时间
T_transfer = 压缩后视频大小 / 带宽
T_decode_check = FFmpeg decode-to-null 离线解码校验耗时
```

说明：视频实验中的“压缩”对应视频转码或降码率重编码；“解码校验”对应 FFmpeg decode-to-null 的完整可解码性检查，不等同于播放器真实播放耗时，但其耗时计入 S1/S2/S3 的主端到端传输时延。S0 仍作为不重新编码的直接传输基线。

## 3. 对比方案

本次实验保留 1 个直传基准组和 3 个视频压缩/转码方案。

| 方案 | 实验角色 | 实验输入 | 处理方式 | 完整性检查 |
|---|---|---|---|---|
| S0 原始 H.264 直传 | base-line | 原始视频文件 | 不重新编码，直接按目标 packet size 分片传输 | 文件可读取、视频流可解码 |
| S1 H.264 降码率重编码 | 兼容优先方案 | 原始 H.264 视频 | 使用 H.264/AVC 重新编码，降低码率或提高 CRF | 输出文件可读取、可解码、时长和分辨率一致 |
| S2 H.265/HEVC 转码 | 主压缩方案 | 原始 H.264 视频 | 转码为 H.265/HEVC，降低同等主观质量下的体积 | 输出文件可读取、可解码、时长和分辨率一致 |
| S3 AV1 转码 | 高压缩对照方案 | 原始 H.264 视频 | 转码为 AV1，观察高压缩率上限和边缘设备计算开销 | 输出文件可读取、可解码、时长和分辨率一致 |

说明：

- S0 不是压缩算法，而是端到端传输基准。
- S1 在**同种编码下的再压缩**，通过调整编码参数压缩文件，用于代表兼容性最好的边缘部署方案。
- S2 是本次实验的**主推荐**压缩方向，最佳的“性价比”平衡点：H.265 能在保证和 H.264 差不多画质的前提下，将视频体积减小约 30%-50%。这个压缩效率的提升非常显著，是当前**工业界应用最广、性价比最高**的升级路径。。
- S3 用于评估**高压缩**算法在边缘设备上的可行性，应重点关注编码耗时是否过高。

## 5. 实验过程

本次实验分为两个层次：实际转码测量层和端到端传输计算层。

| 层次 | 实验内容 | 输出 |
|---|---|---|
| 实际测量层 | 对每个视频样本分别运行 S0、S1、S2、S3，每个方案重复 3 次 | 平均压缩后大小、平均压缩时间、平均解码校验时间、完整性检查结果 |

## 6. 指标定义

### 6.1 压缩比

```text
compression_ratio = compressed_size_bytes / original_size_bytes
```
- 压缩比越小，越适合低带宽情况。

### 6.2 压缩吞吐率

```text
compression_throughput_MBps = original_size_MB / compression_time_s
```
- 视频主端到端流程：视频重新编码->传输新编码的文件->接收端 FFmpeg 解码校验；解码校验耗时计入主端到端时延。
- 压缩吞吐率越高，表示在同一原始视频工作量口径下，发送端的编码速度越快。

### 6.3 解码校验吞吐率

```text
decode_check_throughput_MBps = original_size_MB / decode_check_time_s
```
- 解码校验吞吐率越高，表示在同一原始视频工作量口径下，接收端完成离线可解码性检查的速度越快。
- 该指标既用于评估弱 CPU profile 下的播放适用性风险，也对应端到端时延中的解码阶段。

### 6.4 传输时间

```text
T_transfer_s = compressed_size_bytes * 8 / (bandwidth_mbps * 1,000,000)
```

对于 S0：

```text
T_direct_s = original_size_bytes * 8 / (bandwidth_mbps * 1,000,000)
```

### 6.5 端到端传输时延

```text
T_video_s = avg_compression_time_s + T_transfer_s + avg_decode_time_s
```

对于 S0 原始直传，`avg_compression_time_s = 0`，并继续使用 `T_video_s = T_direct_s` 作为直接传输基线；S1/S2/S3 则完整计入编码、压缩后传输和 FFmpeg 解码校验三个阶段。

### 6.6 端到端时延缩短率

```text
latency_reduction_pct = (T_direct_s - T_video_s) / T_direct_s * 100%
```

### 6.7 解码实时倍率

```text
decode_realtime_factor = source_duration_s / decode_check_time_s
```

- `decode_realtime_factor > 1` 表示离线解码速度快于实时播放速度，弱 CPU 下播放风险较低。
- `decode_realtime_factor < 1` 表示至少存在样本离线解码慢于实时播放，真实播放时可能出现掉帧或卡顿风险。

### 6.8 完整性检查

视频实验不能只做字节级一致性检查，因为 H.264 降码率、H.265 和 AV1 都是有损视频编码。完整性检查应采用结构一致性和可解码性检查：

| 检查项 | 判定标准 |
|---|---|
| 视频可解码 | 完整解码过程无错误 |
| 时长一致 | 输出时长与原始时长偏差在允许阈值内 |
| 分辨率一致 | 默认保持原始分辨率，不主动缩放 |
| 帧率合理 | 输出帧率与原始帧率一致或在允许阈值内 |

如果后续报告需要讨论“压缩后是否还能看清海面、船只、浮标或监测目标”，可以补充VMAF指标。
- VMAF（视频多方法评估融合）是Netflix开发的开源客观质量指标，通过机器学习融合多个基础图像特征，旨在**最大程度地预测和逼近人眼对视频质量的主观评分**，是YouTube等流媒体巨头评估画质的主力工具。


## 7. 分析方式

实验完成后建议按以下角度分析：

| 分析角度 | 目的 |
|---|---|
| 按算法比较压缩比 | 判断 H.264 降码率、H.265、AV1 的体积收益 |
| 按算法比较压缩吞吐率 | 判断边缘设备是否能实时或准实时运行 |
| 按算法比较解码校验吞吐率和实时倍率 | 判断接收端播放或解码压力 |
| 按带宽比较 T_video | 判断低带宽下压缩收益是否能覆盖编码开销 |
| 按 packet size 比较 packet_count | 判断不同传输分片大小下的包数量变化，估计额外的协议开销，验证分包的可行性 |
| 按视频属性解释差异 | 结合分辨率、码率、时长解释压缩收益差异 |
- 如果后续加入包头、ACK、丢包重传或每包处理开销，packet size 才会进一步影响端到端传输时延
- 压缩吞吐率用于判断发送端在线重编码可行性；解码校验吞吐率和解码实时倍率用于判断接收端弱 CPU 播放适用性。
- 如果 AV1 过慢，可标记为**离线**高压缩对照方案。

分算法结论
- S1 H.264 降码率：综合表现最好，在多数视频和带宽条件下都能降低传输体积，同时编码开销可控，因此最适合作为实时或准实时边缘视频传输的主方案。
- S2 H.265/HEVC：在 12 个场景中最优，主要优势出现在低带宽或较大视频文件场景。它压缩率更高，但编码时间更长，因此只有当传输节省能够覆盖编码开销时才更优。
- S0 原始直传：在 9 个场景中最优，主要出现在较高带宽条件下。说明当网络带宽充足、原始视频体积不大或压缩开销不划算时，直接传输反而可能获得更低端到端时延。
- S3 AV1：本实验中没有成为最优方案。其压缩能力与S2接近且编码解码压缩时间过长，不纳入考虑。

- 大视频（≈100 MB，文件1）：传输时间占比极高，H.265 的高压缩比能节省大量传输时间，虽然编码慢但总时延仍能降低 → 适合 S2

- 中视频（3~15 MB，文件2~6）：压缩收益可观，编码开销可控，H.264 降码率最稳 → 适合 S1

- 小视频（≈1 MB，文件7）：本身传输就很快，压缩节省的传输时间不足以覆盖编码开销 → 适合 S0 直传

```text
group_reduction_bandwidth = mean(reduction_of_group_files_at_the_same_bandwidth)
```

## 9. 实验结果说明
- 文件2、3的压缩比为什么高？
    - 文件 2 和文件 3虽然在总码率上与其他样本接近，但二者均为 1280×720、30 fps 视频，相比其他 320×240 或 640×368 样本，在相近码率下需要承载更多像素信息，说明其单位像素码率更低，原始视频可能**已经处于较强压缩状态**。因此再次进行 H.264 降码率或 H.265 转码时，可进一步压缩的冗余空间较小，表现为 S1/S2 压缩比明显高于其他样本。同时，二者编码和解码耗时也显著高于其他文件，使得在中高带宽下，压缩节省的传输时间不足以覆盖处理开销，从而出现负优化。文件 3 的 S1 压缩比达到 0.776，压缩收益尤其有限，因此其负优化现象更明显。
    - 文件 1 的核心原因就是原始码率和原始体积都明显高，所以它和文件 2、3 的情况相反：它有**足够大的传输时间节省空间**，可以抵消 H.265 的编码开销。
