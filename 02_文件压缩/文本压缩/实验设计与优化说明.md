# 海底观测数据按包压缩传输实验设计报告

## 1. 任务目标

本实验面向“海底文件压缩传输”场景。海底边缘节点采集气象、波浪、海流等观测数据后，在发送前按 packet 进行压缩；岸基侧接收压缩数据后解压并恢复原始数据内容。

核心问题：

在不同链路带宽、不同 packet size 和不同边缘算力条件下，五类压缩方式的端到端效率如何？何时应选择 Gorilla、Chimp、gzip、Parquet+ZSTD 或 Parquet+Snappy？

端到端总时延定义为：

```text
T_total = T_compress + T_transfer + T_decompress
```

端到端时延缩短率定义为：

```text
latency_reduction = (T_direct - T_total) / T_direct * 100%
```

其中：

```text
T_direct = 原始文件直接传输时间
```

## 2. 实验设置

- 压缩位置：海底边缘节点
- 解压位置：岸基接收端
- 压缩方式：per-packet 独立压缩
- 分包方式：记录级分包，尽量接近目标 packet size，但不切断完整数据记录
- 对比算法：Gorilla、Chimp、gzip、Parquet+ZSTD、Parquet+Snappy
- 对比基线：未压缩直接传输
- Packet size：512、1448、4096 bytes
- 链路带宽：2 Mbps、4 Mbps、10 Mbps
- 边缘算力限制：CPU limit 100%、50%、20%、10%
- 重复次数：每组实验建议重复 5 次，取中位数
- 完整性检查：压缩、解压后检查数据格式和内容是否发生变化

需要注意：本实验中的 packet size 指压缩前的原始 packet 大小。实验流程采用“先分包，再逐包压缩”，而不是“先整体压缩，再切包”。

## 4. 五种算法的输入与预处理

五种算法从相同原始数据文件出发，但输入形式不同。所有必要的解析、格式转换和恢复过程均应计入压缩或解压耗时。

| 方法 | 实验名称 | 输入对象 | 计入压缩耗时的预处理 |
| --- | --- | --- | --- |
| gzip | Raw bytes + gzip | 原始文件字节 | 无额外字段解析，仅使用记录级 packet 原始字节 |
| Gorilla | Parsed TS + Gorilla | 解析后的时间序列 | 解析时间列、转换时间戳、提取数值列、组织为列式时间序列 |
| Chimp | Parsed TS + Chimp | 解析后的时间序列 | 与 Gorilla 相同，保证二者输入一致 |
| Parquet+ZSTD | Typed table + Parquet(ZSTD) | 类型化表格 | 解析 CSV/TSV/log，构建 typed table，再写入 Parquet(ZSTD) |
| Parquet+Snappy | Typed table + Parquet(Snappy) | 类型化表格 | 与 Parquet+ZSTD 相同，仅 Parquet codec 改为 Snappy |

| 算法 | 实验输入 | 预处理内容 | 完整性检查口径 |
| --- | --- | --- | --- |
| gzip | packet 原始字节流 | 仅进行记录级分包，不解析字段 | 解压后字节级一致 |
| Gorilla | packet 内时间戳和多列数值序列 | 解析时间列、转换为整数时间戳、提取数值列、按列组织为时间序列 | 时间戳、列数、数值内容一致 |
| Chimp | packet 内时间戳和多列浮点数值序列 | 与 Gorilla 相同，保证二者输入完全一致 | 时间戳、列数、数值内容一致 |
| Parquet+ZSTD | packet 内表格记录 | 解析 CSV/TSV/log，建立 schema，转换为 typed table，写入 Parquet 并使用 ZSTD | schema、行数、列数、字段值一致 |
| Parquet+Snappy | packet 内表格记录 | 与 Parquet+ZSTD 相同，仅 codec 改为 Snappy | schema、行数、列数、字段值一致 |

海流日志数据需要特殊说明：

| 输入视图 | 适用算法 | 说明 |
| --- | --- | --- |
| raw log packet | gzip | 直接压缩日志原始字节 |
| structured log table | Parquet+ZSTD、Parquet+Snappy | 将日志解析为 timestamp、level、message、raw_hex、JSON 字段等表格数据 |
| structured ADCP numeric series | Gorilla、Chimp | 从 adcp_preprocessing_data 中抽取数值字段，作为海流时间序列输入 |

因此，Gorilla 和 Chimp 不直接压缩完整日志文本，而是压缩日志中解析出的结构化数值时间序列。

## 5. Packet 数据集构建

本实验采用记录级 packet 构建方式：

```text
原始文件
-> 读取完整记录
-> 按目标 packet size 聚合记录
-> 不切断 CSV 行、TSV 行、日志行或 JSON 片段
-> 形成 packet_512、packet_1448、packet_4096 三组输入
```

记录级分包的原因：

- Gorilla 和 Chimp 需要完整时间戳和数值字段。
- Parquet 需要完整行记录才能构建表格。
- 日志数据中单行可能包含完整 JSON 或 ADCP 记录，不能随意字节切断。
- gzip 也使用同一批记录级 packet，以保证不同算法的实验输入规模一致。

如果后续需要模拟底层链路硬切包，可作为补充实验增加 byte-level packet，但主实验不采用该口径。

## 7. 评价指标

| 指标 | 计算方式 | 越优方向 |
| --- | --- | --- |
| 压缩比 | compressed_size / original_size | 越低越好 |
| 压缩吞吐率 | original_size_MB / T_compress_s | 越高越好 |
| 解压吞吐率 | original_size_MB / T_decompress_s | 越高越好 |
| 端到端总时延 | T_compress + T_transfer + T_decompress | 越低越好 |
| 端到端时延缩短率 | (T_direct - T_total) / T_direct * 100% | 越高越好 |
| 完整性检查 | 解压后格式和内容是否变化 | 必须通过 |

传输时间计算：

```text
T_transfer = compressed_size_bits / bandwidth_bps
```

直接传输时间计算：

```text
T_direct = original_size_bits / bandwidth_bps
```

当前已完成 CPU limit = 100% 条件下的一轮正式实验。该实验使用全部 packet；其中 Gorilla/Chimp 使用 Rust native release 实现，并将解析时间序列预处理计入压缩耗时。

| 数据集 | 最小时延缩短率 | 中位数时延缩短率 | 最大时延缩短率 |
| --- | ---: | ---: | ---: |

gzip 在不同 packet size 下的压缩比如下：

| 数据集 | 512 bytes | 1448 bytes | 4096 bytes |
| --- | ---: | ---: | ---: |
| D1_big_buoy_weather | 0.433 | 0.334 | 0.296 |
| D2_weather_utf16 | 0.307 | 0.183 | 0.141 |
| D3_wave_sensor | 0.500 | 0.364 | 0.324 |
| D4_ocean_current_log | 0.143 | 0.143 | 0.143 |

实验中可以观察到：

- gzip 在四类文件上均能显著降低传输字节数，同时压缩和解压计算开销很低。
- 对 D1、D2、D3 这类结构化时间序列文件，packet size 从 512 增大到 4096 后，gzip 压缩比明显下降，即压缩效果更好。
- D4 海流日志的 gzip 压缩比约为 0.143，且几乎不受 packet size 影响，说明日志文本中存在大量重复结构，gzip 能稳定利用这种重复性。
- Gorilla/Chimp 计入时间序列解析预处理后，中位压缩耗时分别约为 1161.47 ms 和 1219.96 ms，中位解压耗时分别约为 26.56 ms 和 31.02 ms。
- Gorilla/Chimp 在 D2、D3 等结构化数值时间序列上可以产生有效压缩，但压缩后字节数仍高于 gzip，同时计入解析预处理后的压缩耗时也高于 gzip。
- 在当前公平预处理口径下，Gorilla/Chimp 相对 gzip 既没有更小传输体积，也没有更低总计算开销，因此在 2/4/10 Mbps 场景下没有出现超过 gzip 的带宽拐点。
- Parquet+ZSTD 和 Parquet+Snappy 在小 packet 独立压缩场景下受到 schema、footer、metadata 开销影响，多个场景中压缩比大于 1，即压缩后体积反而大于原始数据。

需要说明：当前正式实验只完成了 CPU limit = 100% 的一轮结果。CPU limit = 50%、20%、10% 的边缘低算力实验尚未补跑，因此低算力条件下的算法选择仍需后续用 cpulimit 或等效限速方式继续验证。

## 14. 小结

本实验的主判断标准不是单独的压缩比，而是：

```text
完整性检查通过的前提下，选择 T_total 最低的算法。
```

根据 CPU limit = 100% 的正式实验，可以形成以下结论：

- **在当前 per-packet 压缩传输口径下，gzip 是四类文件的最优端到端算法。** 它在全部 36 个场景中均取得最低 `T_total`，并且完整性检查全部通过。
- **gzip 的优势来自“压缩率足够好 + 计算开销很低”。** 在 2、4、10 Mbps 带宽下，gzip 减少的传输时间足以覆盖其压缩/解压开销。
- **计入各自预处理后，Gorilla/Chimp 仍未超过 gzip，而且差距更清晰。** 它们需要解析时间戳和数值列，压缩后体积也高于 gzip，因此同时输在计算项和传输项。
- **对按包实时传输而言，优先看压缩后字节数和端到端总时延，而不是只看算法 codec 本身速度。** 当前结果说明预处理成本会显著影响 Parsed TS 类算法。
- **Parquet 类方法不适合小 packet 独立压缩。** 当每个 packet 单独写成 Parquet 时，schema 和 metadata 开销会显著削弱甚至抵消压缩收益；Parquet 更适合批量或整文件列式存储压缩。
- **Gorilla/Chimp 的适用前提是纯数值时间序列输入、较长上下文和较高链路带宽。** 当前 per-packet 独立压缩会切短时间序列上下文，限制这类算法发挥；后续应补充整文件或更大批量时间序列实验。
- **packet size 增大通常有利于压缩效果。** D1、D2、D3 中 gzip 在 4096 bytes 下的压缩比均优于 512 bytes，说明较大的 packet 能提供更好的局部冗余上下文。
- **低算力场景仍需单独补测，不能只按 CPU 直觉下结论。** 当前 CPU=100% 结果中，Gorilla/Chimp 计入解析预处理后的压缩耗时高于 gzip；CPU limit 降低后，解析和格式转换成本可能被进一步放大。

推荐方法选择如下：

| 场景 | 推荐方法 | 原因 |
| --- | --- | --- |
| 原始文件按包实时传输 | gzip | 无需解析，字节级无损，端到端时延最低 |
| 日志文件按包传输 | gzip | 日志重复结构明显，压缩比稳定约 0.143 |
| 512 bytes 小 packet | gzip | Parquet 元数据开销过大，Gorilla/Chimp 上下文较短 |
| 1448 / 4096 bytes packet | gzip | 压缩比进一步改善，同时计算开销仍很低 |
| 结构化时间序列高带宽传输 | 可继续评估 Gorilla/Chimp | 仅当数据源已天然输出数值时间序列、且可减少解析成本时才有优势空间 |
| 结构化时间序列离线/批量压缩 | 可继续评估 Gorilla/Chimp | 建议改用整文件或批量时间序列实验，而不是每包独立压缩 |
| 表格数据批量或整文件存储 | 可继续评估 Parquet+ZSTD | 当前 per-packet 口径不利于 Parquet |
| CPU 低算力场景 | 待 cpulimit 补测 | 需要同时观察计算项放大和传输项占比，不能只用 CPU limit 推断 |

最终结论：在当前“记录级分包、每包独立压缩、传输带宽 2/4/10 Mbps、CPU limit = 100%、Gorilla/Chimp 使用 Rust native 实现、各算法计入自身预处理”的实验条件下，gzip 是四类海洋观测文件的统一推荐算法。重新计入预处理后可以进一步确认：Gorilla/Chimp 在按包实时传输场景下不适合直接替代 gzip；后续若要论证 Gorilla/Chimp 或 Parquet 的优势，应改做整文件/批量实验、减少预处理成本，或扩展到更高带宽和原生结构化时间序列输入场景。

整文件实验中的最优算法分布如下：

整文件实验 B 的结论：

- **Parquet+ZSTD 在整文件场景下明显恢复优势。** D1、D2、D3 的 Parquet+ZSTD 压缩比均低于 gzip，说明实验 A 中 Parquet 表现差主要来自“小 packet 重复写 schema/footer/metadata”的实验口径，而不是 Parquet/ZSTD 本身不适合表格数据。
- **端到端最优不只由压缩比决定。** D2 中 Parquet+ZSTD 压缩比最低，但 gzip 在全部 9 个端到端场景胜出，原因是 D2 文件规模相对中等，Parquet 构表和解压开销抵消了传输节省。
- **低带宽时 Parquet+ZSTD 更容易胜出。** D1 在 2 Mbps 下选择 Parquet+ZSTD，而 4/10 Mbps 下 gzip 更优；D3 在 2/4 Mbps 下选择 Parquet+ZSTD，而 10 Mbps 下 gzip 更优。这说明带宽越低，压缩体积优势越重要。
- **D4 海流日志整文件场景出现 Chimp 优势。** D4 从日志中抽取的 ADCP 数值时间序列经 Chimp 压缩后压缩比最低，低/中带宽下 Chimp 端到端最优；10 Mbps 下 Parquet+ZSTD 因计算和传输折中更优。
- **整文件/批量传输不应直接沿用实验 A 的 gzip 结论。** 实验 A 推荐 gzip 用于实时按包独立压缩；实验 B 中，若允许整文件或批量传输，Parquet+ZSTD 应作为表格类数据的重点候选算法。

推荐选择规则：

| 场景 | 推荐方法 |
| --- | --- |
| 实时按包传输 | gzip |
| 整文件表格/批量传输，低带宽 | 优先评估 Parquet+ZSTD |
| D2 类中等规模 UTF-16 气象表 | gzip 端到端更稳 |
| D3 类传感器表格整文件传输 | 2/4 Mbps 选 Parquet+ZSTD，10 Mbps 选 gzip |
| D4 海流日志提取数值时间序列后批量传输 | 2/4 Mbps 选 Chimp，10 Mbps 可选 Parquet+ZSTD |
