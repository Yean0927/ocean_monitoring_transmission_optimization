# Docker 弱 CPU 环境下压缩算法可实现性复现实验设计报告

## 1. 实验目标

本实验不是重新设计新的压缩方案，而是在 Docker 弱 CPU 环境中复现现有的文本/时间序列压缩实验和视频压缩实验，并将 Docker 结果与原先在本机环境下得到的结果进行对比，用于验证压缩算法在边缘弱算力环境中的可实现性。

本实验包含两部分：

```text
实验 A：文本/时间序列压缩复现实验
实验 B：视频压缩/转码复现实验
```

对比目标：

``` text
本机原始实验结果  vs  弱 CPU 复现实验结果
```

核心问题：

- 原实验中有效的压缩算法在 Docker 弱 CPU 环境中是否仍能成功运行？
- 弱 CPU 是否显著改变压缩耗时、解压耗时和端到端总时延？
- 原实验中的最优算法在弱 CPU 环境下是否仍然可行？
- 视频压缩方案在弱 CPU 下是否仍具备可接受的编码/解码开销？

端到端总时延仍采用原实验定义：

```text
T_total = T_compress + T_transfer + T_decompress
```

端到端时延缩短率定义为：

```text
latency_reduction = (T_direct - T_total) / T_direct * 100%
```

其中：

```text
T_direct = 原始文件不压缩直接传输时间
T_transfer = 压缩后文件大小 / 带宽
```

本阶段的 Docker 实验只验证压缩算法可实现性，不引入缓存策略、协议选择和 ns-3 动态链路仿真。缓存、协议选择和海底链路动态变化应放入后续联合实验。

## 3. Docker 弱 CPU 模拟

### 3.1 模拟方式

Docker 用于统一实验环境，并通过容器资源限制模拟弱 CPU。

资源限制包括：

| 限制项 | 作用 |
|---|---|
| CPU quota | 限制容器可用 CPU 计算资源 |
| CPU affinity | 可选，限制容器使用的 CPU 核心集合 |
| Memory limit | 限制容器可用内存 |
| Docker image | 固定 Python、PyArrow、Rust codec、FFmpeg 等依赖版本 |
- CPU quota（CPU 配额）限制容器在固定调度周期内可使用的 CPU 时间，例如每 100ms 中只允许使用 50ms，就是等效 0.5 CPU 时间资源，但不改变容器可见核心数
- Docker image：确保依赖的版本和二进制文件完全一致，彻底避免了“在我电脑上能跑”的环境不一致问题

文本和视频实验用同一个扩展镜像：

| 实验 | 镜像要求 |
|---|---|
| 文本/时间序列压缩 | Python、pandas、PyArrow、Rust native codec |
| 视频压缩 | Python、FFmpeg、libx264、libx265 |

视频实验必须保证 Docker 中 FFmpeg 支持：

```text
libx264
libx265
```

否则 S1、S2 无法与原视频实验结果直接对比。

### 3.2 树莓派 Edge profile

为保证论文实验参数严谨，Docker 弱 CPU profile 直接按照明确的树莓派板型定义。各树莓派板型官方 CPU 核心数均为四核，因此主实验中 Edge-S、Edge-M、Edge-L、Edge-XL 均设置为 4 个 Docker 可见核心，即统一使用 `--cpuset-cpus 0-3`。不同板型之间不通过减少核心数区分，而是通过 `--cpu-period` / `--cpu-quota` 限制每个调度周期内容器可累计使用的 CPU 时间总量。

这样设计的原因是：视频编码、Parquet、ZSTD、PyArrow 等负载可能利用多线程。如果把 Edge-S/M/L/XL 同时设置成不同核心数，就会同时改变“板型算力”和“算法并行度”，导致论文结果难以解释。因此主实验固定 4 个可见核心，使用 CPU 时间配额模拟不同树莓派板子的弱算力差异。

| Profile | 对应硬件 | 官方硬件规格 | Docker 可见核心数 | 内存限制 | CPU 总配额（四核共享） | 实验角色 |
|---|---|---|---:|---:|---|---|
| Host-Docker | 宿主机 Docker 环境 | 不限制 CPU 和内存，用于检查 Docker 环境差异 | 不限制 | 不限制 | 不限制 | Docker 复现基线 |
| Edge-S | Raspberry Pi Zero 2 W | 四核 Cortex-A53 1GHz，512MB SDRAM | 4 核 | 512MB | 容器总配额 20ms/100ms（0.20 vCPU；均摊约 5ms/核/100ms） | 极弱边缘节点 |
| Edge-M | Raspberry Pi 3 B+ | 四核 Cortex-A53 1.4GHz，1GB SDRAM | 4 核 | 1GB | 容器总配额 40ms/100ms（0.40 vCPU；均摊约 10ms/核/100ms） | 低算力边缘节点 |
| Edge-L | Raspberry Pi 4 B | 四核 Cortex-A72，当前官方规格页列为 1.8GHz；内存可选 1GB/2GB/4GB/8GB | 4 核 | 2GB | 容器总配额 80ms/100ms（0.80 vCPU；均摊约 20ms/核/100ms） | 常见弱边缘节点 |
| Edge-XL | Raspberry Pi 5 | 四核 Cortex-A76 2.4GHz，RAM 可到 16GB | 4 核 | 4GB | 容器总配额 160ms/100ms（1.60 vCPU；均摊约 40ms/核/100ms） | 较强边缘节点/对照组 |

说明：

- Edge-S、Edge-M、Edge-L 是本实验的弱 CPU 主体。
- Edge-XL 不是“弱 CPU”主结论，而是较强边缘节点对照组，用于观察性能随板型升级后的变化。
- Host-Docker 不是边缘节点，只用于检查 Docker 环境相对本机原实验是否引入明显偏差。
- 主实验固定 4 个 Docker 可见核心，避免把“CPU 核心数变化”和“弱算力限制”混在同一个变量中。
- `--cpu-quota` 是容器在一个 `--cpu-period` 周期内的累计 CPU 时间总量，不是每个核心单独可用的 CPU 时间。例如 Edge-XL 的 160ms/100ms 表示容器整体最多使用 1.60 vCPU；如果平均摊到 4 个可见核心，约为 40ms/核/100ms，但实际调度不保证严格均摊。


### 3.3 Docker 参数映射方法

Docker 可以严格限制内存、可见核心集合和可用 CPU 时间，但不能直接把 x86 宿主机变成 ARM Cortex-A53/A72/A76，也不能直接设置“1GHz/1.4GHz/1.8GHz/2.4GHz”这类真实芯片频率。因此论文中应将参数分为两层：

| 参数层 | 内容 | 处理方式 |
|---|---|---|
| 目标硬件 profile | Edge-S/M/L/XL 的官方 CPU 架构、频率、硬件核心数和内存规格 | 作为实验分组和论文描述依据 |
| 并行结构控制 | Docker `--cpuset-cpus` | 主实验统一设置为 `0-3`，即 4 个可见核心，保持算法并行度一致 |
| 总算力控制 | Docker `--cpu-period` / `--cpu-quota` | 固定调度周期为 100ms，不同 profile 限制容器累计 CPU 时间总量为 20ms、40ms、80ms、160ms；该总量由 4 个可见核心共享 |
| 内存控制 | Docker `--memory` / `--memory-swap` | 按目标板型 profile 设置，并令 `memory-swap = memory`，避免 swap 掩盖内存限制 |

主实验 Docker 参数表如下。`--cpu-period 100000` 表示调度周期为 100ms；`--cpu-quota` 表示每 100ms 内容器最多可累计使用多少微秒 CPU 时间。该配额是容器总量，不是单核心配额。例如 `--cpu-quota 20000` 表示容器每 100ms 最多累计使用 20ms CPU 时间，等效总 CPU 资源约为 0.20 vCPU。

| Profile | Docker `--cpuset-cpus` | Docker `--memory` | Docker `--memory-swap` | Docker `--cpu-period` | Docker `--cpu-quota` | 可读解释（容器总量；四核共享） | 等效 CPU 资源 |
|---|---|---:|---:|---:|---:|---|---:|
| Host-Docker | 不限制 | 不限制 | 不限制 | 不限制 | 不限制 | 不限制，用于复现本机基线 | 不限制 |
| Edge-S | `0-3` | 512MB | 512MB | 100000 | 20000 | 20ms/100ms 总配额；均摊约 5ms/核/100ms | 0.20 vCPU |
| Edge-M | `0-3` | 1GB | 1GB | 100000 | 40000 | 40ms/100ms 总配额；均摊约 10ms/核/100ms | 0.40 vCPU |
| Edge-L | `0-3` | 2GB | 2GB | 100000 | 80000 | 80ms/100ms 总配额；均摊约 20ms/核/100ms | 0.80 vCPU |
| Edge-XL | `0-3` | 4GB | 4GB | 100000 | 160000 | 160ms/100ms 总配额；均摊约 40ms/核/100ms | 1.60 vCPU |

上述参数对应的 Docker 运行约束为：

```text
Edge-S:  --cpuset-cpus 0-3 --memory 512m --memory-swap 512m --cpu-period 100000 --cpu-quota 20000
Edge-M:  --cpuset-cpus 0-3 --memory 1g   --memory-swap 1g   --cpu-period 100000 --cpu-quota 40000
Edge-L:  --cpuset-cpus 0-3 --memory 2g   --memory-swap 2g   --cpu-period 100000 --cpu-quota 80000
Edge-XL: --cpuset-cpus 0-3 --memory 4g   --memory-swap 4g   --cpu-period 100000 --cpu-quota 160000
```

论文中应明确报告以下参数，而不是只写“弱 CPU”或“百分比限制”：

```text
Target board profile: Edge-S / Edge-M / Edge-L / Edge-XL
Visible Docker cores: 4
Docker CPU period/quota: 100000/20000, 100000/40000, 100000/80000, 100000/160000
Readable CPU budget: 每 100ms 分别最多使用 20ms、40ms、80ms、160ms CPU 时间
Memory limit: 512MB, 1GB, 2GB, 4GB
```

该设计是“基于官方板型规格和 Docker 资源约束的近似 profile”。它能保证实验可复现、参数可报告，但不能声称 Docker 完全等价真实 Raspberry Pi 的 ARM 微架构、缓存层级和真实主频。

### 3.4 Docker 与本机结果的解释口径

本实验最终不是单纯比较 Docker 和本机谁更快，而是比较：

```text
Edge-S/M/L/XL 是否导致原本可行的压缩方案变得不可行
Edge-S/M/L/XL 是否改变最优算法排序
Edge-S/M/L/XL 是否使压缩计算开销超过传输节省
```

因此，重点指标不是绝对运行时间，而是：

- 压缩耗时增幅。
- 解压耗时增幅。
- 端到端时延缩短率是否仍为正。
- 最优算法是否发生变化。
- 完整性是否仍然通过。

### 4.1 数据集

| 数据集 | 来源文件 | 数据类型 | 说明 |

### 4.2 压缩与分片顺序

文本压缩实验使用 `03_compression_evaluation/03_compression_evaluation/code/seven-codec-comparison.py` 作为七算法统一实验脚本。由于本阶段没有引入协议包头开销，Docker 主复现实验不再比较 512、1448、4096 三种分包大小，只保留 4096 bytes 作为统一传输分片大小。

主复现实验采用“先压缩、再分片”的顺序：

```text
原始文件/完整数据集记录集合
-> 对完整对象运行文本压缩算法
-> 得到完整压缩结果
-> 按 4096 bytes 统计传输分片数量
-> 估算传输时间和端到端总时延
```

因此，`packet_size=4096` 在本轮 Docker 实验中只表示压缩完成后的传输分片大小，不表示压缩前的 packet 构建大小。先分包再压缩的文本实验不再进入正式统计。

### 4.3 压缩算法

Docker 文本复现实验使用七种算法。相比原五算法，新增 LZ4 和 ZSTD-3；这两种与 gzip 一样属于直接压缩原始源文件/packet bytes 的字节级无损算法，不解析字段、不构建时间序列、不构建表格。

| 算法 | 输入对象 | 预处理 | 完整性检查 |
|---|---|---|---|
| LZ4 | 原始源文件/packet bytes | 无字段解析，直接压缩原始字节流 | 解压后字节级一致 |
| ZSTD-3 | 原始源文件/packet bytes | 无字段解析，ZSTD level=3 直接压缩原始字节流 | 解压后字节级一致 |
| gzip | 原始 packet bytes | 无字段解析 | 解压后字节级一致 |
| Gorilla | 时间戳和多列数值序列 | 解析时间列、提取数值列 | 时间戳、列数、数值内容一致 |
| Chimp | 时间戳和多列浮点序列 | 与 Gorilla 相同 | 时间戳、列数、数值内容一致 |
| Parquet+ZSTD | typed table | 解析 CSV/TSV/log，写入 Parquet ZSTD | schema、行数、列数、字段值一致 |
| Parquet+Snappy | typed table | 解析 CSV/TSV/log，写入 Parquet Snappy | schema、行数、列数、字段值一致 |

### 4.4 文本实验参数矩阵

| 参数 | 取值 |
|---|---|
| Dataset | D1、D2、D3、D4 |
| Algorithm | LZ4、ZSTD-3、gzip、Gorilla、Chimp、Parquet+ZSTD、Parquet+Snappy |
| Transfer fragment size | 4096 bytes |
| Bandwidth | 2、4、10 Mbps |
| Edge profile | Host-Docker、Edge-S、Edge-M、Edge-L、Edge-XL |

重复次数采用原文本实验设计中的 5 次，便于和原结果口径保持一致。如果论文需要更稳健统计，可以在 Docker 正式复现实验中额外补充 10 次重复，但主对比表应先按原实验 5 次口径输出。

### 5.2 视频压缩方案

Docker 视频复现实验只保留 S0-S2 三种方案。S3/AV1 因编码开销过高，不进入本轮 Docker 弱 CPU 正式实验。

| 方案 | 实验角色 | 处理方式 | 完整性检查 |
|---|---|---|---|
| S0 原始 H.264 直传 | baseline | 不重新编码，直接传输原始文件 | 文件可读取、视频流可解码 |
| S1 H.264 降码率重编码 | 兼容优先方案 | 使用 H.264/AVC 重新编码 | 输出可读取、可解码、时长和分辨率一致 |
| S2 H.265/HEVC 转码 | 主压缩方案 | 转码为 H.265/HEVC | 输出可读取、可解码、时长和分辨率一致 |

需要强调：视频 Docker 实验要实际运行 FFmpeg 转码和解码验证，而不是只读取文件大小。这样才能与原视频压缩实验在同一口径下比较弱 CPU 下的编码可行性。视频压缩脚本使用 `adaptive-protocol-selection-package/compression_scripts/run_video_compression_experiment.py`。视频端到端统计采用先完成整体编码/转码、再按 4096 bytes 传输分片的口径。

### 5.4 视频实验输出

Docker 视频实验输出应与原视频实验保持一致：

| 文件 | 说明 |

## 6. 与本机原结果的对比方法

### 6.1 对比维度

文本和视频实验均采用相同的对比逻辑：

```text
本机原始结果
vs
Host-Docker 复现结果
vs
Edge-S/M/L/XL 弱 CPU 结果
```

其中：

- 本机原始结果用于表示已有实验结论。
- Host-Docker 用于检查 Docker 环境本身带来的偏差。
- Edge-S/M/L/XL 用于观察树莓派级弱 CPU 对算法可实现性的影响。

### 6.2 关键对比指标

| 指标 | 对比目的 |
|---|---|
| compression_ratio | 验证压缩后体积是否基本一致 |
| compressed_size_bytes | 检查不同环境下输出大小是否稳定 |
| compression_time_ms | 观察弱 CPU 对压缩端计算开销的影响 |
| decompression_time_ms | 观察弱 CPU 对解压端计算开销的影响 |
| T_total | 判断端到端总时延是否仍有收益 |
| latency_reduction_pct | 判断压缩是否仍优于直接传输 |
| best_algorithm | 判断最优算法是否发生变化 |
| integrity | 判断算法是否仍能完整恢复数据 |
| failure_rate | 判断弱 CPU 下是否出现失败或超时 |

### 6.3 归一化对比指标

为了避免只看绝对耗时，建议增加相对变化指标。

压缩耗时放大倍数：

```text
compress_slowdown = docker_compression_time_ms / host_compression_time_ms
```

解压耗时放大倍数：

```text
decompress_slowdown = docker_decompression_time_ms / host_decompression_time_ms
```

端到端时延变化：

```text
total_latency_delta_pct = (docker_T_total - host_T_total) / host_T_total * 100%
```

压缩比偏差：

```text
ratio_delta_pct = (docker_compression_ratio - host_compression_ratio) / host_compression_ratio * 100%
```

如果压缩比和压缩后大小基本一致，但压缩/解压耗时显著上升，则说明算法本身仍正确，但弱 CPU 可能影响其部署可行性。

### 6.4 最优算法变化分析

对每个场景比较：

```text
host_best_algorithm
host_docker_best_algorithm
edge_s_best_algorithm
edge_m_best_algorithm
edge_l_best_algorithm
edge_xl_best_algorithm
```

重点观察：

- Host-Docker 是否复现了本机最优算法。
- 弱 CPU 是否让高计算开销算法失去优势。
- gzip / S0 / S1 这类低开销方案是否在弱 CPU 下更容易胜出。
- Parquet+ZSTD、H.265 等高压缩高开销方案是否只在低带宽下仍然可行。

## 7. 实验指标

### 7.1 压缩比

```text
compression_ratio = compressed_size_bytes / original_size_bytes
```

越低表示压缩后数据越小。

### 7.2 压缩吞吐率

```text
compression_throughput_MBps = original_size_MB / compression_time_s
```

用于评估边缘节点侧压缩开销。

### 7.3 解压吞吐率

```text
decompression_throughput_MBps = original_size_MB / decompression_time_s
```

用于评估接收端恢复开销。

### 7.4 传输时间

```text
T_transfer_s = compressed_size_bytes * 8 / (bandwidth_mbps * 1,000,000)
```

直接传输基线：

```text
T_direct_s = original_size_bytes * 8 / (bandwidth_mbps * 1,000,000)
```

### 7.5 端到端总时延

```text
T_total_s = T_compress_s + T_transfer_s + T_decompress_s
```

### 7.6 端到端时延缩短率

```text
latency_reduction_pct = (T_direct_s - T_total_s) / T_direct_s * 100%
```

如果该值为正，说明压缩后整体传输更快。如果为负，说明压缩计算开销超过了传输节省。

### 7.7 完整性检查

文本/时间序列：

| 算法 | 完整性检查 |
|---|---|
| LZ4 | 解压后字节级一致 |
| ZSTD-3 | 解压后字节级一致 |
| gzip | 解压后字节级一致 |
| Gorilla | 时间戳和数值列一致 |
| Chimp | 时间戳和数值列一致 |
| Parquet+ZSTD | schema、行数、列数、字段值一致 |
| Parquet+Snappy | schema、行数、列数、字段值一致 |

视频：

| 方案 | 完整性检查 |
|---|---|
| S0 | 原文件可读取、可解码 |
| S1 | 输出可读取、可解码、分辨率和时长一致 |
| S2 | 输出可读取、可解码、分辨率和时长一致 |

### 7.8 失败率

```text
failure_rate = failed_repeats / total_repeats * 100%
```

失败原因包括：

- 压缩失败。
- 解压失败。
- 完整性不一致。
- Docker 内存不足。
- FFmpeg 编码失败。
- FFmpeg 解码失败。
- 运行超时。

## 8. 可实现性判定规则

算法或视频方案分为三类。

| 等级 | 判定标准 | 说明 |
|---|---|---|
| 可实现 | 完整性通过，Docker 弱 CPU 下稳定运行，且多数场景 `latency_reduction_pct > 0` | 可进入后续缓存和协议联合实验 |
| 有条件可实现 | 完整性通过，但只在低带宽、大文件或部分数据集上有收益 | 作为条件策略保留 |
| 不建议部署 | 完整性失败、弱 CPU 下失败率高、运行时间过长或长期劣于直传 | 不进入后续联合实验 |

建议增加弱 CPU 下的超时规则：

```text
如果 T_compress + T_decompress 超过 T_direct 的 2 倍，
或视频单次转码超过预设最大运行时间，则标记为不建议部署或单独说明。
```

## 10. 实验执行顺序

建议按以下顺序执行，避免一开始就运行全部长耗时视频实验。

| 步骤 | 内容 | 目的 |
|---|---|---|
| 1 | Host-Docker 文本 smoke test | 确认数据路径、依赖、Rust codec 可用 |
| 2 | Host-Docker 视频 smoke test | 确认 FFmpeg 和 S1/S2 编码器可用 |
| 3 | Host-Docker 完整复现文本实验 | 检查 Docker 与本机结果差异 |
| 4 | Host-Docker 完整复现视频实验 | 检查 Docker 与本机视频结果差异 |
| 5 | Edge-S/M/L 文本实验 | 验证树莓派弱 CPU profile 下文本压缩可实现性 |
| 6 | Edge-S/M/L 视频实验 | 验证树莓派弱 CPU profile 下视频压缩可实现性 |
| 7 | Edge-XL 文本和视频对照实验 | 观察较强边缘节点下是否恢复接近本机结论 |
| 8 | 合并本机与 Docker 结果 | 生成对比表和可实现性结论 |

S3/AV1 不进入本阶段正式结果统计；如后续需要单独论证 AV1，可作为补充实验另行设计，不与本轮 S0/S1/S2 可实现性结果混合。

## 11. 与后续联合实验的关系

本阶段只输出压缩方案在 Docker 弱 CPU 条件下的可实现性结论。

后续联合实验建议只保留本阶段通过验证的方案：

```text
可实现方案 -> 进入压缩 + 缓存 + 协议选择 + ns-3 联合实验
有条件可实现方案 -> 仅在对应数据类型或低带宽条件下进入联合实验
不建议部署方案 -> 不进入后续联合实验
```

这样可以避免后续联合实验出现组合爆炸，也能保证 ns-3 阶段只评估真实可部署的压缩候选方案。

## 12. 阶段结论写作口径

本阶段论文结论建议写成：

```text
To evaluate deployability under edge computing constraints, the text/time-series and video compression experiments were reproduced inside Docker containers with controlled CPU limits. The text experiment used a seven-codec comparison including LZ4 and ZSTD-3 as direct raw-byte compression methods, while the video experiment used FFmpeg-based transcoding schemes. The Docker results were compared with the original host-based results using the same datasets, packet sizes, bandwidth assumptions, and repetition counts. Feasibility was determined by integrity pass rate, failure rate, compression/decompression overhead, end-to-end latency reduction, and whether the best algorithm changed under weak CPU constraints.
```

不建议写成：

```text
Docker 完全等价真实树莓派硬件。
本阶段已经完成缓存和协议选择联合优化。
视频实验只读取文件大小即可证明弱 CPU 编码可行。
```

更准确的总结是：

```text
本阶段通过 Docker 弱 CPU 复现实验，验证原压缩实验结论在资源受限边缘环境下是否仍然成立，并筛选可进入后续缓存和 ns-3 联合实验的压缩候选方案。
```
