# Docker 弱 CPU 环境下文本压缩算法可实现性实验报告

## 1. 实验目标

本实验面向海洋观测文本、日志和时间序列数据还有视频文件，验证现有文本压缩算法和视频压缩算法在 Docker 弱 CPU profile 下的可实现性，并与本机不受限的基线结果进行对照。

本实验的目的：弱CPU环境下的可行性验证，只是测量能够支撑对应压缩算法运行的大概环境。由于弱CPU环境下不一定可能完全复现未受限的主机性能，因此实验会在压缩方案生效（起到较好优化效果时停止）。

注意：本实验未考虑协议开销（协议头里的各种字段开销），因此分包的大小未作为实验参数考虑。

## 2. 在 Docker 模拟的弱 CPU 环境

### 2.1 宿主机环境

本轮 Docker 实验运行在同一台宿主机上，宿主机配置如下。该配置用于解释 Docker profile 的基线性能边界；由于本实验使用 CPU 编码与 CPU 压缩算法，独立显卡不参与压缩计算。

| 项目 | 配置 |
|---|---|
| 宿主机 | 2024 联想拯救者 R9000P |
| CPU | AMD Ryzen 9 7945HX with Radeon Graphics，16 物理核心|
| Docker 环境 | Docker Desktop / Docker Engine 29.6.2 |
| 电源适配器与性能模式 | 135W，均衡模式 |
| 视频编码实现 | FFmpeg `libx264` / `libx265` CPU 编码，未使用 NVENC 硬件编码 |

说明：Docker `--cpu-quota` 并不会改变宿主机 CPU 的真实主频，也不会把 x86 CPU 变成 ARM 树莓派 CPU；它通过 Linux CFS 调度限制容器在每个 `--cpu-period` 周期内可累计获得的 CPU 运行时间。因而本文中的 Docker 弱 CPU profile 更准确地说是“CPU 时间配额/调度节流”模拟，可近似表达可用算力下降或类似降频后的计算受限状态，但不能复刻真实树莓派的 ARM 微架构、缓存层级、内存带宽、温控和供电降频行为。

- 正式 Docker 结果只统计S1 和 S2；S3/AV1 在视频压缩实验中，压缩比与S2方案接近，且性能开销远大于S2故不参与后续的实验。

| 方案 | 方案名 | 输出编码 |  实验定位 | 本轮状态 |
|---|---|---|---|---|
| S1 | h264_lower_bitrate | H.264 | 兼容性较强的降码率方案 | 正式统计，重复 10 次 |
| S2 | h265_hevc | H.265/HEVC |  主压缩方案，压缩率更高但计算开销更大 | 正式统计，重复 5 次 |

视频压缩算法的原理：
- 首先在发送端将视频按指定编码方式进行编码，编码后得到一个文件，实际传输时传输这个文件
- 接着，接收端接收到这个文件后，在视频播放器中一边解编码进行播放，不存在解压缩开销。
- 经过此过程的视频文件，分辨率、帧率、时长等基本属性保持不变。 但码率（比特率）一定会降低，同时画质会下降。一般为有损压缩。

### 4.2 视频压缩实验结果

视频压缩后的传输时延 = 编码时间 + 传输重编码后的文件的时间 （不计算解码时间）
- 解码是在播放视频时进行的。
- 解码时间指的是实验中使用 FFmpeg 库对压缩后视频文件进行完整性检查时，完整解码或读取验证视频流所消耗的离线校验时间。
- 本文不将解码校验时间计入视频传输端到端时延，而将其作为压缩结果可解码性与弱 CPU 解码负担的辅助指标。

为进一步区分内存限制和 CPU quota 对可实现性的影响，本轮补充运行了 4C-0.2V-2GB 与 4C-0.4V-2GB：CPU quota、可见核心数、packet size、带宽和重复次数保持不变，仅将 Docker `--memory` 与 `--memory-swap` 均设置为 2GB。
