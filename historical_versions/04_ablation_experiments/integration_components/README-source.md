## 联合实验的接入约束

```text
N0 本地样本记录/媒体片段
    → 接入链路
N1 应用层接收 → 按数据流组装 → 实际编码 → 待发队列
    → N1—N2 动态瓶颈 → N2 路由转发 → N3 完整接收、解压/解码
```

N1 需要终止上游应用连接并创建下游连接，才能操作文件内容；普通 IP 转发不能压缩应用文件。下游自适应方案根据发送时的当前链路和实际业务特征调用模型，静态方案使用 TCP CUBIC。连接重建、未完成传输、重传和切换开销均需统计，不能仅替换链路容量。

拓扑沿用第一阶段 TCP 程序；按其动态驱动设置，接入/出口链路为 100 Mbps、传播时延 0 ms，瓶颈单向传播时延为当前 RTT/2。第一阶段错误模型安装在瓶颈两端接收设备上，因此数据和 ACK 两个方向都可能丢包。每 30 秒应用当前观测点，队列和连接连续保留，禁止阶段间重置后再拼接结果。

第三阶段参考记录参数：D1 76 B/12 s，D2 43 B/12 s，D3 128 B/0.02 s，D4 1041 B/120 s，V1 195875 B/s，I1 258715 B/s。实际文本行长与参考大小不同，按固定记录频率回放时，需记录真实生成字节数，不能同时宣称原始 Mbps 精确不变。视频应按字节生成速率累积真实文件片段，不能把整个几 MB 的视频当成每秒一条 195875 B 记录。I1 可使用原始大小中位数对应的真实图片，每秒一张。

五组为 FULL、WO_PROTOCOL、WO_COMPRESSION、WO_CACHE、BASELINE。所有组使用同一份来源事件和链路时序。启用缓存时采用 50 MB、Priority-MaxF；No-Cache 不保留等待发送队列。所有组完成文件组装所需的内存必须一致并单独计量，否则无法公平开展整文件压缩消融。

文本和视频需调用第二阶段相应编码实现，对每个实际组装批次/完整媒体文件重新执行，保留输入输出哈希、实际大小与处理耗时。算法配置可来自 2 Mbps、不限 CPU 条件下的选择；旧报告中的比率和处理耗时不得作为新传输负载。图片用上述实际 payload 接口。

端到端时间从源记录产生到 N3 解压/解码完成计算，包含生成后的组装等待、编码、排队、接入与瓶颈传输、重传及解码。丢失率依据原始记录/完整文件统计，同时另报未完成组装、待发和在途数据；压缩文件部分分片到达不能算整个原始文件已送达。仿真结束仍在等待的数据不能自动算永久丢失。

## 尚需确定的组装触发条件

用户尚未确定：严格达到原文件大小才发送，或达到大小阈值/最长等待时间之一即发送。后者需要明确各类文本最长等待时间。不能在未确认时偷偷缩小文件目标或按整文件比例代替小批次编码。

`inputs/source-inventory.json` 保存原始字节数、文件行数及按参考频率逐行回放所需时间。行数包含表头，不等同于最终传感器观测条数；它用于发现组装周期问题。D1 全部文件行按 12 秒一行回放需约 73 天，D2 约 16 天，D3 约 390 秒，D4 三份日志约 1.2 天。因此 60 分钟实验若严格以整文件为目标，多数文本不会产生完整可压缩文件。
